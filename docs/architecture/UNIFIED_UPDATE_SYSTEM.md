# AirDeck Unified Update System

Status: binding architecture target for implementation.

## 1. Goal

AirDeck needs one reliable update system that derives available versions from the authoritative GitHub release/build pipeline and presents the correct installable update for every supported AirDeck deployment.

Targets include:

- Windows Standalone;
- Server/Web installation;
- Docker;
- Android;
- iOS/iPadOS;
- Demo deployment;
- first-party helper services/tools;
- supported bundled/managed dependencies;
- future AirDeck first-party clients.

`git pull` is not the end-user update mechanism. Git/GitHub is the source/build/release authority; users install verified platform artifacts produced by CI/CD.

## 2. One release graph

All AirDeck surfaces participate in one version/release graph.

A release manifest should describe which artifacts belong to one AirDeck release and their compatibility.

Conceptual example:

```json
{
  "release": "1.8.0",
  "channel": "stable",
  "coreApi": "1.x",
  "commit": "<git-sha>",
  "artifacts": {
    "windows-x64": {"version":"1.8.0","asset":"...","sha256":"..."},
    "server-linux-x64": {"version":"1.8.0","asset":"...","sha256":"..."},
    "docker": {"version":"1.8.0","image":"...","digest":"sha256:..."},
    "android": {"version":"1.8.0","distribution":"store"},
    "ios": {"version":"1.8.0","distribution":"app-store"}
  }
}
```

The exact schema must be versioned and machine-readable.

## 3. GitHub / CI release source

The update service reads trusted release metadata generated from GitHub/CI, not arbitrary repository contents at runtime.

Recommended flow:

```text
merge/tag/release
      ↓
GitHub Actions
      ↓
build + test each platform
      ↓
sign/notarize/package
      ↓
publish artifacts/images/store build
      ↓
generate signed release manifest
      ↓
AirDeck Update Service / clients
      ↓
compatibility + channel + platform check
      ↓
Update available
```

Do not offer an update simply because the repository contains a newer commit. Only a successful, published, verified release artifact is installable.

## 4. Channels

Support at least:

- `stable` — normal users;
- `beta` — opt-in preview;
- `nightly/development` — developers/testers only, if enabled.

Changing channel requires appropriate permission and must be visible in settings.

Production installations must not silently move from stable to development builds.

## 5. Update UI

Add a first-class `Updates` area under the signed-in user/settings/system surface.

Show:

- installed AirDeck version;
- Git commit/build id where useful;
- update channel;
- latest compatible version;
- release date;
- release notes/changelog;
- security/critical indicator;
- platform artifact status;
- Core/API compatibility;
- required migrations;
- dependency updates;
- download/install progress;
- restart/reboot/service impact;
- last successful/failed update;
- rollback availability.

Actions according to platform/permission:

- Check for updates;
- Download;
- Install now;
- Install on restart/maintenance window;
- Skip/defer optional version;
- Change channel;
- Roll back where supported.

## 6. Windows Standalone

Windows updates should use a signed installer/updater artifact from the release pipeline.

Target behavior:

1. query manifest;
2. choose correct architecture/artifact;
3. verify signature/hash;
4. download to staging;
5. verify package again;
6. prepare config/database backup where needed;
7. stop only required AirDeck services cleanly;
8. install atomically where possible;
9. run migrations;
10. restart services/UI;
11. healthcheck;
12. commit update or offer rollback.

Do not overwrite user media/config/secrets with release defaults.

The updater must account for active playout: it must not unexpectedly interrupt an on-air station. Support explicit maintenance windows / operator confirmation for disruptive updates.

## 7. Server/Web installation

Server updates use a packaged release/deployment mechanism rather than executing arbitrary Git repository code as root.

Requirements:

- preflight disk/database/config checks;
- backup/snapshot hooks;
- maintenance mode;
- service drain/stop;
- package/container replacement;
- database migrations;
- service restart;
- healthcheck;
- rollback metadata.

Self-hosted operators can disable automatic installation while retaining update notifications.

## 8. Docker

Docker updates are image-based.

Use immutable image tags/digests generated by CI. AirDeck can report a newer compatible image and, when the deployment grants permission, orchestrate or provide the exact supported update action.

Never mutate application source inside a running container with `git pull`.

Recommended model:

- version tag such as `airdeck:1.8.0`;
- channel aliases such as `stable`/`beta` for discovery only;
- record immutable digest in update history;
- pull new image;
- migrate with controlled job/startup phase;
- replace service;
- healthcheck;
- retain prior image/digest for rollback.

Docker Compose deployments should receive/update a versioned Compose/deployment manifest where required.

## 9. Android

Android distribution must follow Android platform/store rules.

For public production distribution, AirDeck detects that a newer compatible app version exists and routes installation/update through the approved app distribution mechanism (normally Google Play or an explicitly supported enterprise/private distribution path).

Do not implement a hidden self-updater that bypasses platform security/store policy.

AirDeck may still show unified release notes, Core compatibility and server-update warnings inside the app.

## 10. iOS / iPadOS

iOS/iPadOS updates follow Apple distribution rules. AirDeck may detect/display that an update is available and link/open the approved App Store/TestFlight distribution path as appropriate, but must not self-install executable application updates outside Apple's mechanism.

The unified release manifest still records compatibility so an older iOS client can warn when a server/Core update would exceed its supported API range.

## 11. Demo

The Demo follows the same release graph. It is the only environment for AirDeck live update testing.

Before a stable rollout, update behavior must be exercised on the designated Demo, including migrations, service restart, rollback and compatibility checks.

No update-development live test may target a production/customer/real station.

## 12. Dependency updates

AirDeck must track managed runtime dependencies separately from AirDeck application versions.

Examples may include:

- Icecast;
- ezstream;
- Liquidsoap;
- FFmpeg/codecs where bundled/managed;
- Node/runtime components;
- database engine/client migrations where AirDeck manages them;
- helper services;
- bundled frontend/runtime packages;
- AirDeckCast/lautCast helpers;
- extension runtime/SDK compatibility.

For each dependency record:

- installed version;
- managed vs externally managed;
- compatible range;
- latest AirDeck-approved version;
- security relevance;
- restart impact;
- source/license;
- update method;
- rollback capability.

AirDeck must not blindly install the newest upstream dependency. CI/release engineering approves a tested version/range and publishes it in the release/dependency manifest.

## 13. Extension updates

The Extensions system integrates with the unified updater but remains a separate trust domain.

Core update preflight must check installed extensions for compatibility. If an extension is incompatible with the target AirDeck version, show it before installation and support disable/quarantine/migration policy rather than allowing AirDeck to fail on startup.

Extension updates require their own package signatures, permissions and publisher trust checks.

## 14. Compatibility matrix

Every release should declare compatibility among:

- AirDeck Core;
- HTTP API major/minor capability set;
- realtime/event contract;
- Windows client;
- Web/Server/Docker;
- Android;
- iOS/iPadOS;
- Extensions SDK/manifest version;
- schema/database version;
- managed dependency bundle.

An update must be blocked or clearly staged when it would create a known incompatible combination.

## 15. Database/config migrations

Updates that change persistent state require explicit migrations.

Rules:

- migrations are versioned;
- backup/snapshot before destructive migration;
- migration state recorded;
- safe retry/idempotency where practical;
- downgrade/rollback feasibility declared;
- config migrations preserve user settings/secrets;
- failed migration stops rollout and enters recoverable state.

Never silently reset configuration to defaults to make an update succeed.

## 16. Security and supply chain

Required:

- HTTPS/TLS;
- signed release metadata or equivalent trusted verification;
- SHA-256 or stronger artifact integrity;
- Windows code signing;
- Apple/Android platform signing;
- immutable Docker digests;
- CI provenance/build metadata where practical;
- no execution of unsigned arbitrary downloads;
- no updater shell command constructed from untrusted manifest text;
- rollback protection for critical security migrations where required;
- audit of update checks/install attempts/results;
- least-privilege updater/service permissions;
- secrets never included in release artifacts/logs.

A compromised public GitHub description/release note must not be sufficient to execute code. Installability derives from trusted artifacts/signatures and manifest policy.

## 17. Update service API

Integrate update state into the complete AirDeck API.

Conceptual resources:

- current version/build/capabilities;
- available release for current platform/channel;
- release manifest/release notes;
- compatibility preflight;
- dependency status;
- update job/status/progress;
- maintenance-window scheduling;
- update history;
- rollback status.

Exact paths must be reconciled with the real AirDeck router/OpenAPI inventory.

Protected update actions require strong RBAC/admin permission and audit.

## 18. Automatic checks vs automatic installation

Default recommended behavior:

- automatically **check** for updates;
- notify administrators/users appropriately;
- security/critical updates receive stronger visibility;
- actual disruptive installation is permission/policy controlled;
- server/Windows stations may configure maintenance windows;
- mobile app installation follows the platform store;
- Docker auto-update is opt-in and compatibility gated.

Never restart an on-air system simply because a new release exists.

## 19. Update coordinator

Introduce a Core-side `UpdateCoordinator` responsible for:

- platform/deployment detection;
- release channel;
- manifest retrieval/cache;
- signature/integrity verification;
- compatibility calculation;
- dependency/extension preflight;
- update job lifecycle;
- maintenance policy;
- progress/events;
- audit/history;
- post-update healthcheck;
- rollback coordination.

Platform-specific installers are adapters beneath the coordinator, not independent update systems.

## 20. Platform adapters

Conceptual adapters:

- `WindowsInstallerUpdateAdapter`;
- `ServerPackageUpdateAdapter`;
- `DockerImageUpdateAdapter`;
- `AndroidStoreUpdateAdapter`;
- `AppleStoreUpdateAdapter`;
- dependency-specific managed adapters.

This keeps update policy/version discovery consistent while respecting OS distribution rules.

## 21. Realtime notifications

Update events should use the common AirDeck event contract, e.g. conceptually:

- update.available;
- update.download.started/progress/completed;
- update.preflight.failed;
- update.install.scheduled;
- update.install.started;
- update.install.completed;
- update.install.failed;
- update.rollback.started/completed/failed;
- dependency.update.available;
- client.incompatible.

Exact event names must match the eventual shared event convention.

## 22. Release automation

GitHub Actions should eventually produce a release matrix rather than manually uploaded unrelated files.

Pipeline stages:

1. determine semantic version/channel;
2. build Core/server/web;
3. build Windows artifact/installer;
4. build/push Docker image;
5. build Android release artifact for store pipeline;
6. build iOS artifact/store pipeline where macOS signing infrastructure is available;
7. run tests/security scans;
8. sign/notarize artifacts;
9. publish artifacts/images/store submissions;
10. generate hashes/digests/provenance;
11. generate release manifest;
12. publish only when required gates pass.

A partially failed release must not be advertised as universally available. The manifest records per-platform availability.

## 23. Rollout strategy

Support staged rollout metadata where useful:

- Demo first;
- optional beta cohort;
- stable rollout;
- emergency pause/revoke.

This is not permission to live-test on production. Development/live verification remains Demo-only. Staged production rollout happens only after a release has passed the release gates.

## 24. Backup and rollback

Where technically possible, maintain rollback information for the immediately previous release.

Rollback is not always possible after irreversible schema/security changes; the updater must say so before installation.

Windows/server/Docker should preserve enough prior artifact/deployment metadata for a controlled rollback when supported.

## 25. Offline/manual update

Self-hosted AirDeck installations may need offline/manual updates.

Support a verified update bundle/import flow where practical:

- administrator downloads official signed artifact/manifest elsewhere;
- imports it into AirDeck;
- AirDeck verifies signature/hash/version/compatibility;
- same preflight/install/migration/healthcheck pipeline runs.

Manual does not mean unverified.

## 26. Completion criteria

Do not call the update function complete merely because AirDeck can compare a GitHub version string.

Completion requires:

**release pipeline -> signed/versioned manifest -> correct platform artifact -> compatibility preflight -> verified staging -> platform-appropriate install -> migrations -> restart/store handoff -> healthcheck -> history/rollback**, plus dependency/extension compatibility and API/UI status.

Live verification of the update pipeline is performed only on the designated AirDeck Demo.
